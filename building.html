Building hipObject#

Prerequisites#

Required#

  • CMake 3.25.2 or later

  • ROCm 7.14 or later (provides HIP, HSA runtime)

  • C++20 capable compiler and standard library: GCC 13 or later, or Clang (e.g., amdclang++ from ROCm) with GCC 13’s libstdc++ or later. On RHEL 9, whose system GCC is 11, install gcc-toolset-13 or later.

Optional#

  • rdma-core 49 or later development headers (libibverbs-dev or rdma-core-devel), for the test that checks hipObject’s copies of the libibverbs structures against them. The library doesn’t need them, since it loads libibverbs with dlopen.

  • GTest (fetched automatically if not found)

  • libcurl development files (libcurl4-openssl-dev or libcurl-devel), for the examples’ --live mode. Without them, the examples build with only their stub mode.

  • Doxygen, Python 3, Sphinx, Breathe (for documentation)

Run Time#

RDMA needs libibverbs and the libibverbs provider for the NIC, from rdma-core: libibverbs1 and ibverbs-providers on Ubuntu, or libibverbs on RHEL. hipObject loads libibverbs.so.1 with dlopen the first time hipObjInit() runs, so it doesn’t need the development package. Without libibverbs, hipObjInit() prints why libibverbs didn’t load and fails with hipObjRdmaError.

Build Steps#

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"

# Run the tests (no GPU, RDMA NIC, or S3 server needed)
ctest --test-dir build --output-on-failure

# Install (to ROCM_PATH)
sudo cmake --install build

Add -DCMAKE_PREFIX_PATH=/opt/rocm if CMake doesn’t find ROCm’s packages. The tests need no hardware, and the ones that load the system’s libibverbs skip if it isn’t installed. The GPU-direct and RDMA data paths are tested by the emulated-hardware CI workflows, and on lab hardware (see hipObject cuObject Interoperability).

Using hipObject#

A CMake project finds the installed hipObject with find_package(), and links the hipobj::hipobj target:

find_package(hip CONFIG REQUIRED)
find_package(hipobj CONFIG REQUIRED)

add_executable(app app.c)
target_link_libraries(app PRIVATE hipobj::hipobj hip::host)

Configure it with CMAKE_PREFIX_PATH set to where ROCm and hipObject are installed, such as /opt/rocm. The header is installed as include/hipobj/hipobj.h, and the target adds its directory to the include path, so the code includes <hipobj.h>. The header is C, and C11 and C++11 code can include it. A program that calls HIP itself, as one that allocates GPU memory does, links hip::host too.

The README’s Quick Start is a short program to start from. The examples, whose sources are installed in share/doc/hipobject<mm>/examples (see HIPOBJ_INSTALL_EXAMPLES, below), are complete programs that make their S3 requests with libcurl.

CMAKE_BUILD_TYPE can be Debug, Release, RelWithDebInfo, or None. RelWithDebInfo and Release builds are optimized and compile out the library’s assert() checks. They also enable _FORTIFY_SOURCE=3 when building with Clang or GCC 12 and later. Use Debug when developing hipObject or running it under a sanitizer. Multi-config generators, such as Ninja Multi-Config, ignore CMAKE_BUILD_TYPE and pick the configuration at build time.

HIPOBJ_CXX_STANDARD selects the C++ standard that hipObject is built with, without compiler extensions. 26 needs CMake 3.30 or later, which is the first version that knows how to ask GCC (14 and later) and Clang for C++26.

HIPOBJ_BNXT and HIPOBJ_IONIC compile in the queue pair attributes for Broadcom Thor-2 and AMD Pensando NICs. Without them, hipObject still uses those NICs, with its generic attributes.

HIPOBJ_INTEGRATION_TESTS only has an effect when BUILD_TESTING is on.

HIPOBJ_INSTALL_EXAMPLES builds the example programs in the build tree (examples/) and installs their sources, with a CMakeLists.txt that builds them against the installed hipObject, in share/doc/hipobject<mm>/examples (see Packaging). The example programs aren’t installed. The README.md installed with them explains how to build and run them.

HIPOBJ_INSTALL_TOOLS builds and installs the tool programs, in bin, in the runtime package (see Packaging). So far there’s one, hipobj-test-install, which will check that hipObject is installed and works, as far as the system’s hardware allows. For now it only reports the hipObject version, with --version.

HIPOBJ_WERROR adds -Werror to hipObject’s own targets (the library, tests, examples, and tools), but not to third-party code that CMake fetches. It’s off by default so that a compiler hipObject hasn’t been tested with can’t break the build with a new warning. CI turns it on, and developers should too.

HIPOBJ_USE_CODE_COVERAGE builds hipObject with LLVM’s source-based code coverage instrumentation. It needs Clang (or ROCm’s amdclang) as both the C and C++ compiler, and the llvm-profdata and llvm-cov from the same LLVM version, which CMake looks for next to the compiler. Set HIPOBJ_LLVM_PROFDATA and HIPOBJ_LLVM_COV if it doesn’t find them. Run the tests, then build the hipobj-coverage target to report the coverage of the library’s sources:

cmake -B build -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
  -DHIPOBJ_USE_CODE_COVERAGE=ON
cmake --build build
(cd build && ctest)
cmake --build build --target hipobj-coverage

The report goes in coverage/report.txt (a summary for each file) and coverage/lines.txt (the coverage of each line) in the build directory. Every instrumented program writes its profile to coverage/profraw in the build directory, however it’s run, and the profiles add up over runs, so delete coverage/profraw to start over. Since the programs write to the build directory, don’t install or package a coverage build.

HIPOBJ_USE_SANITIZERS builds hipObject with every sanitizer except ThreadSanitizer that the compiler supports and that can be combined with AddressSanitizer:

  • With GCC and Clang: AddressSanitizer (including LeakSanitizer), UndefinedBehaviorSanitizer, and the float-divide-by-zero check.

  • With GCC: the bounds-strict, float-cast-overflow, pointer-compare, and pointer-subtract checks.

  • With Clang: the implicit-conversion, local-bounds, and nullability checks.

Clang doesn’t get pointer-compare and pointer-subtract, since in an optimized build they report comparisons and subtractions that the optimizer made, not just the ones in the code. With Clang, cmake/sanitizer-ignorelist.txt turns the implicit-conversion checks off in the C++ standard library headers, whose conversions are deliberate.

HIPOBJ_USE_THREAD_SANITIZER builds hipObject with ThreadSanitizer. ThreadSanitizer can’t be combined with AddressSanitizer, so only one of these two options can be on. Use a separate build directory for each.

Both options need GCC or Clang (including ROCm’s amdclang), and the C and C++ compilers must be the same kind. Configuring checks that the compilers can build a program with the sanitizers, and fails if, for example, the sanitizer runtimes aren’t installed:

cmake -B build-asan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
  -DHIPOBJ_USE_SANITIZERS=ON
cmake --build build-asan
(cd build-asan && ctest)

The sanitizers instrument everything that hipObject compiles: the library, the tests and other programs, and the third-party code that it builds from source. A sanitizer build always downloads and builds GoogleTest, rather than using an installed copy, so that GoogleTest is instrumented too. Libraries that come from the system or from ROCm, such as the HIP runtime, are not instrumented.

Every sanitizer report is fatal, so a test with a report fails. Each program that hipObject builds sets some of the sanitizers’ run-time options, such as the one that turns on GCC’s pointer-compare and pointer-subtract checks (see cmake/sanitizer-default-options.c). The ASAN_OPTIONS, UBSAN_OPTIONS, and TSAN_OPTIONS environment variables override them.

HIPOBJ_SANITIZER_SHARED_RUNTIME links programs with the shared library version of the sanitizer runtime. Libraries from another build that also uses the shared runtime, such as a sanitizer build of ROCm, can then be used in the same program. If the runtime isn’t in a directory that the dynamic linker searches, as with Clang’s, the programs get an RPATH to it. When the option is OFF, programs link the static runtime instead, and the shared libhipobj leaves the runtime’s symbols for the program to provide.

The option defaults to what the compiler does without it: ON with GCC, and OFF with Clang. Clang 18’s shared runtimes (Ubuntu 24.04’s, at least) ignore the run-time options that hipObject’s programs set, so with them, for example, ThreadSanitizer doesn’t stop at the first report. Turn the option on with Clang 19 or later to test against a sanitizer build of ROCm, which uses Clang’s shared runtime.

If ThreadSanitizer stops a program at startup with an “unexpected memory mapping” error, the kernel’s address space layout randomization uses more bits than ThreadSanitizer supports. Reduce it with sudo sysctl vm.mmap_rnd_bits=28.

HIPOBJ_USE_CLANG_TIDY runs clang-tidy (19 or later) on hipObject’s own code as it compiles. It needs Clang as the C++ compiler. Configuring looks on PATH for clang-tidy, then for versioned names such as clang-tidy-23, newest first, and then in ROCM_PATH/llvm/bin, and passes over any older than 19. ROCm’s clang-tidy comes last because it’s built without the clang-analyzer-* checks. Set HIPOBJ_CLANG_TIDY_EXE to the path of the one to use. HIPOBJ_USE_IWYU runs include-what-you-use the same way; its suggestions don’t fail the build. Use a separate build directory for it, with Clang as the compiler: when the compiler is a newer Clang than the one include-what-you-use was built with (such as amdclang), the build leaves out the flags that include-what-you-use’s clang doesn’t have, including some hardening flags.

ROCM_PATH and ROCM_VERSION can also be set in the environment. If ROCM_PATH isn’t set but ROCM_VERSION is, ROCM_PATH defaults to /opt/rocm/core-<major>.<minor>. If neither is set, ROCM_PATH defaults to /opt/rocm/core if it contains a ROCm installation, and otherwise to /opt/rocm.

ROCM_VERSION defaults to the version in ROCM_PATH/.info/version, or in ROCM_PATH/core/.info/version when ROCM_PATH is /opt/rocm, which only contains links. Configuring fails if ROCM_VERSION is earlier than 7.14.

Packaging#

hipObject uses rocm-cmake to install and package the library. If ROCm doesn’t provide rocm-cmake, it is downloaded when hipObject is configured. To build DEB or RPM packages, run CPack in the build directory:

cpack -G DEB    # or RPM

DEB package

RPM package

Contents

hipobject<mm>

hipobject<mm>

Shared library, license, tools

hipobject-dev<mm>

hipobject-devel<mm>

Header, CMake package, libhipobj.so link, examples’ sources

A static build (BUILD_SHARED_LIBS=OFF) creates a single hipobject-static-dev<mm> DEB or hipobject-static-devel<mm> RPM package, without the tools. Test programs aren’t packaged. With HIPOBJ_MINIO_CLIENT, the runtime package also has the minio-getput-rdma program (see MinIO C++ RDMA Bridge).

<mm> is the major and minor version of the ROCm that hipObject is built for, as in ROCm’s own package names, so the runtime package for ROCm 10.1 is hipobject10.1. Builds for different ROCm versions are different packages, which install side by side when each installs into its ROCm version’s own directory, /opt/rocm/core-<mm>, as they do when ROCM_VERSION is set (see CMake Options) and as the nightly packages do.

The package version is hipObject’s version followed by the ROCm version with each . replaced by 0, such as 0.1.0.100100 for ROCm 10.1.0, and a release. The release comes from the CPACK_DEBIAN_PACKAGE_RELEASE or CPACK_RPM_PACKAGE_RELEASE environment variable when hipObject is configured, and is local if it isn’t set. An RPM package’s release also ends with the distribution’s tag, such as .el9, when the build machine’s rpm defines one (%{?dist}).

CPack builds DEB packages with dpkg-deb, and RPM packages with rpmbuild. rocm-cmake only sets up the generators whose tools it finds when hipObject is configured.

The development package depends on the runtime package with its own version and release, so the header and the library always come from the same build. Each package replaces the package it was named before it had the ROCm version, which only nightly packages had, so installing it removes that package.

The MinIO program’s libraries, with HIPOBJ_MINIO_CLIENT, are libcurl, OpenSSL, zlib, and the system’s pugixml and curlpp, if it uses them. The RPM packages name libraries by soname, which every distribution’s library packages provide. The static package doesn’t have the program, so it doesn’t depend on its libraries. The examples’ sources need libcurl’s development package to build their --live mode, but the packages don’t depend on it.

The package that holds the library recommends libibverbs, which RDMA needs (see Run Time). It’s a recommendation rather than a dependency so that hipObject can be installed without it, such as on a build machine. apt and dnf install recommended packages by default, but not suggested ones. hipObject doesn’t include libibverbs in its packages. rocm-cmake adds the runtime package’s recommendation or suggestion of the development package.

Nightly Packages#

DEB packages of the develop branch are built every night that it changes, and published as the nightly prerelease, which each new build replaces. There are packages for Ubuntu 24.04 and 26.04, built for ROCm 10.1.0 and 7.14.1 with that version’s amdclang. They install into /opt/rocm/core-<major>.<minor>, so the packages for both ROCm versions can be installed together, and their release is 0.<commit time>.g<commit>~<Ubuntu release>, so a newer nightly upgrades an older one. The nightly packages are for testing, and aren’t a supported release.

MinIO C++ RDMA Bridge#

Build the hipobj_minio library and minio-getput-rdma example with HIPOBJ_MINIO_CLIENT:

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DHIPOBJ_MINIO_CLIENT=ON

cmake --build build

Additional system packages (Ubuntu 24.04):

sudo apt install libssl-dev zlib1g-dev libcurl4-openssl-dev

See integrations/minio-cpp/TESTING.md for lab validation against MinIO AIStor over RDMA.

cuObject Interoperability#

See hipObject cuObject Interoperability for the v1.2.0 compatibility matrix. Build the in-repo RC test server:

cmake -B build -DBUILD_TESTING=ON

cmake --build build --target hipobj-rdma-test-server

Optional cuObject library probes:

cmake -B build \
  -DHIPOBJ_FETCH_CUOBJECT_CLIENT=ON \
  -DHIPOBJ_FIND_CUOBJECT_SERVER=ON \
  -DCUOBJSERVER_ROOT=/opt/nvidia/cuobjserver

Building Documentation#

To build the HTML documentation locally:

cmake -B build \
  -DHIPOBJ_BUILD_DOCS=ON

cmake --build build --target hipobj-sphinx-html

The output appears in build/docs/html/.

For a docs-only build that does not require a ROCm/HIP toolchain:

cmake -B build \
  -DHIPOBJ_DOCS_ONLY=ON \
  -DHIPOBJ_BUILD_DOCS=ON

cmake --build build --target hipobj-sphinx-html

The build installs Sphinx and the other Python packages that docs/sphinx/requirements.txt lists into a virtual environment in the build directory, which needs network access the first time.

The documentation also builds without CMake, with Doxygen and the packages in docs/sphinx/requirements.txt installed. Run Doxygen in docs/doxygen, which writes its XML to docs/doxygen/xml/, and then Sphinx:

(cd docs/doxygen && doxygen Doxyfile)
sphinx-build -b html docs build/docs/html

Environment Variables#

When hipObject is configured:

  • ROCM_PATH: Override the ROCm installation path.

  • ROCM_VERSION: Override the ROCm version.

When a program that uses hipObject runs:

  • LD_LIBRARY_PATH: Only needed if the loader can’t find ROCm’s libraries or libibverbs.so.1 otherwise, such as when they’re installed outside the system’s library directories. The installed library finds the ROCm libraries it was built with by itself.

  • HIPOBJ_NIC_HINT: Read by the examples and the MinIO bridge, not the library: the name of the RDMA device to use (as ibv_devices lists it), which they pass to hipObjInit() as nicHint.

  • HIPOBJ_MAX_TRANSFERS: How many transfers can run at once, from 1 to 1024 (default 16).

  • HIPOBJ_STAGE_TIMEOUT_MS: How long, in milliseconds, a copy to or from a buffer that’s staged through host memory can take, up to 24 hours (default 30000).

  • HIPOBJ_DMABUF: A value starting with 0, n, or N turns off dma-buf registration of GPU memory.

  • HIPOBJ_REQUIRE_GPU_DIRECT: Any value but one starting with 0, n, or N makes hipObjBufRegister() fail rather than stage a GPU buffer through host memory.

  • HIPOBJ_RDMA_DEBUG: Any value not starting with 0 reports failed dma-buf exports on stderr. The MinIO bridge also reports where each of its failed transfers failed.

The library reads the last five in hipObjInit(), each time it runs, and ignores an invalid value, leaving the default (see Architecture).
